# 0006. Use a strictly decoded, versioned JSON inventory file as the interchange format between discover and assess

- Status: Accepted; the reader's implementation (it decodes through one strict decoder shared with
  the snapshot reader) and the quoting of the path in errors (`text.QuotePath`, which keeps the base
  name of a long path) are amended by
  [0009](0009-decode-adapter-json-documents-through-one-strict-decoder.md); the schema version policy
  is amended by [0011](0011-scope-capabilities-and-one-offering-per-tier.md): retiring a vocabulary
  value is not a version change while no tool writes inventory files, and needs a new version once
  `shift2eu discover` does; format version 2, which keeps these rules and adds sizing, usage,
  workload, relations and cost, is added by [0024](0024-json-inventory-file-format-v2.md)
- Date: 2026-11-10

## Context

PRD 2 (issue #2) makes `shift2eu assess --inventory <file>` work offline, before any live source adapter
exists. The file it reads is not a test fixture: a future `shift2eu discover` will write it, and users will
review, sanitise or hand-edit it before assessing it. Once inventories exist in the wild, changing what
they mean is a breaking change, so the format needs a recorded shape and a version policy from the start.

Forces:

- The file is untrusted input. It may be hand-edited, generated by another tool, or come from someone
  else's account. A path on the command line may also name something that is not an inventory at all.
- A silently ignored mistake is worse than a refused file. If a misspelt `capabilites` were ignored, the
  resource would lose its capabilities, and the assessment would report a direct fit where the real fit
  is partial: wrong in the direction that hides blockers.
- Each resource is mapped against every candidate offering of the target, so the number of resources,
  not just the file size, drives the work.
- The domain (`inventory.New`, `text.Validate`, `taxonomy.ParseCategory`, `taxonomy.ParseCapability`)
  already decides which values are valid. Repeating those rules in the adapter would let them drift.
- CLAUDE.md rule 6 prefers the standard library; `encoding/json` is in it.
- The `InventorySource` port (ADR 0005) wants one-line errors that name the input through `text.Quote`
  and never repeat raw input or OS error text.

## Decision

An inventory file is a UTF-8 JSON document (RFC 8259) holding one object, without a byte order mark,
read by `internal/adapter/source/inventoryfile`. This ADR fixes **schema version 1**.

```json
{
  "schemaVersion": 1,
  "source": "aws",
  "resources": [
    {
      "id": "i-0123456789abcdef0",
      "rawType": "AWS::EC2::Instance",
      "category": "compute.vm",
      "region": "eu-west-1",
      "capabilities": ["ipv6"]
    },
    { "id": "global-example", "category": "unclassified" }
  ]
}
```

**Fields.** Keys are spelt exactly as below, character for character once JSON escapes are decoded, and
appear at most once per object. Both are enforced: `"ID"`, `"Capabilities"` or `"capabilitieſ"` (with
U+017F, which Unicode folds to `s`) is an unknown key, and a repeated key is an error, never a silent
choice between two values.

| Field | JSON type | Required | Meaning |
|---|---|---|---|
| `schemaVersion` | integer | yes | Format version; `1` for this ADR |
| `source` | string | yes, not blank | The source the inventory was taken from, for example `aws` |
| `resources` | array of resource objects | yes; may be empty | The resources, in any order |

Each resource object:

| Field | JSON type | Required | Meaning |
|---|---|---|---|
| `id` | string | yes, not blank, unique | The source's identifier for the resource |
| `category` | string | yes | A taxonomy category, `unclassified` included |
| `rawType` | string | no | The source's own type name; absent or empty means unknown |
| `region` | string | no | The source region; absent or empty means a global resource |
| `capabilities` | array of strings | no | Capabilities from the taxonomy vocabulary; order and duplicates do not matter |

`null` is the same as an absent field; an element of `resources` or `capabilities` may not be `null`. The
format has no account, tenant or subscription field.

**Strict decoding.** The reader refuses, with `ErrDecode`: a file that starts with a byte order mark
(UTF-8 `EF BB BF`, or UTF-16 `FF FE` or `FE FF`) or is not valid UTF-8 (`encoding/json` would replace an
invalid byte with U+FFFD, so the IDs in a report would differ from the IDs in the file); anything but one
JSON object (an empty file, malformed JSON, a second value after the object); a key the format does not
define, spelt inexactly or repeated (at the top level or in a resource); a value of the wrong JSON type;
a string, key or value, that escapes a surrogate (U+D800 to U+DFFF) other than as a high surrogate
followed at once by a low one (such an escape names no character, and `encoding/json` would decode it to
U+FFFD as well); and a missing or `null` `resources`. The reader checks keys, types, escapes and counts
by reading the document token by token (`json.Decoder.Token`) before it decodes anything, because
`encoding/json` matches keys ignoring case and keeps the last of a repeated key. Errors name the key by
its path, an array element with its index in brackets as the domain writes it (`resources[1].regoin`),
and place the problem by line and column (`line 3, column 26`, both from 1, the column in characters),
never by byte offset, and never in the decoder's own text.

**Schema version policy.** `schemaVersion` is found before any key or type is checked (the encoding and
the JSON syntax are checked before it), so a file of another version is refused for its version
(`ErrSchemaVersion`, naming the version seen) and never for a field version 1 does not know. The reader
finds it by scanning the top-level keys for the exact key `schemaVersion`, stepping over the other
values; a key that differs only in case is not the version, and is named in the error when the version
is missing. A missing or `null` version is refused the same way; there is no default. The reader accepts
exactly the integer `1`, spelt so: `1.0` and the string `"1"` are refused. Any change to the format, even
a new optional field, is a new version recorded in a new ADR: with strict decoding, a version 1 reader
could not read the new field anyway. A later reader may accept several versions; a writer always writes
one.

**Caps.** The reader reads at most `MaxFileSize` (10 MiB) plus one byte through `io.LimitReader` and
refuses a larger file (`ErrTooLarge`) before decoding it; exactly 10 MiB is accepted. While it reads the
document token by token, it refuses more than `MaxResources` (50,000) resources (`ErrTooManyResources`)
and a resource that lists more than `MaxCapabilities` (32) capabilities (`ErrDecode`): it counts the
elements of `resources` and of each `capabilities` list and stops at the first one past the cap, before a
single resource is decoded, so memory follows the file size, not the counts. (Decoding first would let
10 MiB of empty `{}` resources, about 3 million of them, allocate over 1.5 GiB before the count is
checked.) A resource entry in an exported, indented inventory is roughly 150 to 250 bytes, so the size
and resource caps admit about the same estate. The size cap alone would not bound the mapping work:
10 MiB of minimal resources (`{"id":"r1","category":"unclassified"}` and so on) is roughly 250,000 of
them. The capability vocabulary holds nine capabilities; 32 leaves room for it to grow, and for
duplicates, which the cap counts although the domain drops them.

**Values are validated by the domain.** The reader copies the fields into `inventory.Resource` values
and builds the inventory with `inventory.New`, which enforces a non-blank source, unique non-blank IDs,
free text that passes `text.Validate` (no control or format characters, no edge white space, at most
2048 bytes), and exact categories and capabilities. An unknown category is an error naming the resource
and the category, never `unclassified`. Domain sentinels (`taxonomy.ErrUnknownCategory`,
`inventory.ErrEmptySource`, ...) stay reachable with `errors.Is`. The inventory sorts resources by ID, so
file order never reaches a report.

**Errors.** Every error is one line, starts `inventory file <text.Quote(path)>:`, and wraps `ErrRead`,
`ErrTooLarge`, `ErrDecode`, `ErrSchemaVersion`, `ErrTooManyResources`, a domain sentinel or `ctx.Err()`.
A cancelled context is reported before the file is opened. The text of `*fs.PathError` (which repeats
the path unquoted) and of `encoding/json` errors is never passed on; values from the file, such as an
unknown field name, are shown through `text.Quote`.

**Cancellation and reading once.** The file is opened and read on a goroutine of its own; the call
returns as soon as the context is cancelled, and closes the file if it is open, which ends a read
blocked on a pipe or FIFO. An open that blocks (a FIFO with no writer) cannot be interrupted portably,
and closing does not end a read Go cannot poll (a regular file on a stalled NFS mount): the goroutine
then waits until the open or the read returns or the process exits, which for a CLI is the end of the
run, and the call still returns. Regular files and pipes are read once per call. Whether `assess`
accepts `-` for standard input is a milestone 7 decision; if it does, the CLI reads the input once and
buffers it (ADR 0005), so the adapter still reads a file.

**Fixtures.** Inventory files committed to the repository are sanitised (CLAUDE.md rule 2): IDs such as
`i-0123456789abcdef0` and `db-example`, account `123456789012`, addresses in `192.0.2.0/24`, names under
`example.com`. Inventories taken from real accounts are never committed.

## Alternatives considered

- **YAML.** Friendlier to edit by hand, but it needs a third-party parser, types values implicitly
  (`no` and `on` become booleans), and anchors and aliases let a small file expand into a large
  document. JSON is in the standard library and has one reading.
- **CSV.** Flat: capabilities would need an in-cell list syntax, and the version and source would need a
  header convention of their own.
- **JSON Lines, one resource per line.** Streams, but needs a separate header line for the version and
  source, and streaming buys nothing under the caps (ADR 0005 rejected streaming ports for the same
  reason).
- **Lenient decoding (ignore unknown fields).** Gives forward compatibility for free, but turns a typo
  into lost data and an over-optimistic verdict. Strict reading plus explicit versions makes every
  change visible.
- **Accept unknown versions on a best-effort basis, or minor versions.** The same silent-loss problem as
  lenient decoding. One integer, read strictly, keeps compatibility explicit.
- **Resources as an object keyed by ID.** Makes uniqueness look structural, but `encoding/json` keeps the
  last of two equal keys without a word, so it would hide duplicates that a list lets the domain report.
- **Decode the document, then count its resources.** Simple, but decoding allocates every resource
  before the count is known: about 1.6 GiB for 10 MiB of empty resources. Counting while reading tokens
  bounds memory by the file size.
- **`encoding/json/v2`, which is case-sensitive, refuses repeated keys and refuses invalid UTF-8 by
  default.** It needs `GOEXPERIMENT=jsonv2` in Go 1.27, an experiment the build would depend on. The
  token walk gets the same strictness from the stable `encoding/json`; revisit when v2 is stable.
- **Validate values in the adapter.** Would repeat the domain's rules in a second place, where they
  drift. The future `discover` writer and this reader meet in `inventory.New`.
- **Cap by `Stat` size before reading.** The file can grow between `Stat` and the read, and a pipe has no
  size. Capping what is actually read bounds memory whatever the path names.
- **Cap the file size only.** Does not bound the mapping work (see *Caps*).

## Consequences

- `shift2eu discover`, when it comes, writes version 1 exactly as recorded here, and a round-trip test pins
  that its output reads back to the same inventory.
- The format cannot grow without a version bump and an ADR. That is deliberate friction.
- The version 1 reader leaves no known gap from `encoding/json`: inexact keys, repeated keys, invalid
  UTF-8, byte order marks and escaped lone surrogates, which `encoding/json` lets through and the first
  version of this reader did too, are refused.
- The format has no account field, but IDs can still identify an account (ARNs and Azure resource IDs
  embed account and subscription IDs). Users must treat an inventory file as sensitive; the tool never
  uploads it.
- The caps are constants in the adapter. Raising them is a code change, not a format change. A future
  `discover` writes compact JSON, or this decision revisits the caps first: Azure resource IDs alone are
  130 to 200 characters, so an indented Azure inventory of 50,000 resources may not fit in 10 MiB.
- The reader holds the file in memory and passes over it several times: a syntax check, the version
  scan, the token walk and the decode. At 10 MiB that is cheap (tens of milliseconds); the token walk
  holds one token at a time.
- The adapter reads the file on every call to `Inventory`. A path that can be read only once, such as a
  pipe, serves a single run but not the contract suite's repeat check.
